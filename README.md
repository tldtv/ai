# Агент сигналов для точек роста Авито.Работы

Репозиторий с пайплайном, который по расписанию собирает сигналы из
источников (RSS), размечает их по рынку, отделяет факт от интерпретации
через Claude, формулирует гипотезу возможности с оценкой по рубрике —
и обновляет бэклог и дашборд со светофором.

## Структура

```
config/parameters.yaml      — все управляемые параметры (пороги, веса,
                               источники, целевое окно дат)
data/backlog.csv            — бэклог идей (открывается и в Excel/Sheets)
src/fetch_sources.py        — механический слой: RSS + фильтр + теги + дедуп
src/analyze_signals.py      — смысловой слой: вызов Claude API
src/run_pipeline.py         — точка входа, запускает оба шага по очереди
src/build_dashboard.py      — собирает docs/index.html из backlog.csv
.github/workflows/
  weekly_signal_scan.yml    — расписание (по понедельникам) + ручной запуск
docs/index.html             — дашборд (генерируется, вручную не редактировать)
```

## Установка (один раз)

1. Создайте новый репозиторий на GitHub и загрузите в него все файлы
   этой папки (можно перетащить их в веб-интерфейс GitHub — drag & drop
   работает и для вложенных папок).
2. **Settings → Secrets and variables → Actions → New repository secret**
   — имя `ANTHROPIC_API_KEY`, значение — ключ с console.anthropic.com
   (раздел API Keys → Create Key). Там же привязывается карта — оплата
   идёт по факту использования, при таком объёме сигналов расход
   исчисляется центами в неделю.
3. **Settings → Pages** → Source: *Deploy from a branch* → ветка `main`,
   папка `/docs` → Save. Через минуту-две дашборд будет доступен по
   адресу вида `https://<ваш-логин>.github.io/<название-репозитория>/`.
4. Вкладка **Actions** — если GitHub спросит разрешение на запуск
   workflow, подтвердите.

## Как запускать

- **Автоматически** — каждый понедельник в 06:00 UTC (09:00 МСК), без
  вашего участия.
- **Вручную** — вкладка Actions → Weekly Signal Scan → Run workflow.
  Можно указать `mode=backfill` и даты, чтобы разово пройтись по
  источникам за прошлый период (см. ограничение ниже).

## Важное ограничение backfill

RSS-ленты обычно хранят только последние ~20–50 записей, а не архив за
несколько месяцев назад. Поэтому полностью автоматический backfill за
июнь–август 2026 может не дотянуться до части источников — их лента к
моменту запуска уже "прокрутилась" дальше. Практичный путь: разово
собрать этот период вручную (например, обычным поиском — так же, как
мы делали при тестировании подхода) и вписать найденные строки прямо в
`data/backlog.csv` по существующей схеме колонок. Дальше пайплайн будет
только дополнять этот файл, не перезаписывая его.

## Источники без RSS (Telegram-каналы, сайты без фида)

Пайплайн в этом виде читает только RSS. Источники без своего фида —
Telegram-каналы, сайты без `/feed` — этим кодом автоматически не
читаются. Варианты на следующую итерацию: сервис вроде rss.app,
который генерирует RSS из Telegram-канала или страницы без своего фида,
либо Telegram Bot API, если вы администратор нужных каналов. До тех пор
такие источники проверяются вручную и заносятся в `backlog.csv` так же,
как и результаты backfill.

## Визуал дашборда

Дашборд (`docs/index.html`) — обычный HTML/CSS/JS, который генерирует
`src/build_dashboard.py`. Текущая версия умеет:

- сводная статистика сверху (всего идей + сколько зелёных/жёлтых/красных
  по светофору) — клик по плитке одновременно фильтрует карточки по
  этому цвету;
- вкладки по рынкам (Классифайд/Подработка/HR-tech/Все) с подсказкой
  (значок ⓘ), что означает каждый рынок — текст берётся из
  `config/parameters.yaml -> markets -> <рынок> -> description`;
- фильтр по группе источника (например «РФ/ТГ» и «Мировой» — группы
  свои, задаются в `config/parameters.yaml -> source_groups`, см. ниже),
  с подсказкой (значок ⓘ), что за источники входят в каждую группу —
  список подтягивается из `config/parameters.yaml -> sources`, отдельно
  вести не нужно;
- фильтр по диапазону оценки (ползунок) и по диапазону даты источника
  (календарь);
- сортировка по оценке или по дате источника;
- кнопка «Обновить» рядом с заголовком — ведёт на страницу запуска
  workflow в GitHub Actions (адрес строится из `dashboard -> github_repo`);
  сама кнопка не запускает пайплайн напрямую — встраивать токен с правом
  записи в репозиторий в код статической страницы небезопасно, поэтому
  остаётся один клик «Run workflow» на самой странице Actions;
- на карточке — оценка, статус (у статуса `new` — подсказка «сигнал
  найден N дней назад», число считается на момент сборки дашборда),
  рынок (с подсказкой), группа источника (с подсказкой), id кластера
  (если заполнен), два сворачиваемых блока вместо одного описания —
  «Идея из новости» (факт + интерпретация) и «Применимость для Авито»
  (гипотеза возможности), ссылка на источник, дата, уверенность,
  пометка «вне целевого окна» (если сигнал не попал в окно backfill),
  сворачиваемый блок «Разбивка оценки» (см. ниже — теперь редактируется
  вручную) и сворачиваемый блок «Комментарии»;
- **ручное изменение оценки по критерию** — в блоке «Разбивка оценки»
  каждая цифра (1-5) редактируется прямо в поле ввода; после изменения
  итоговая оценка сигнала и, если нужно, его цвет пересчитываются сразу
  же (формула та же, что в `analyze_signals.py` — взвешенное среднее по
  `priority_weights`), а изменённая строка подсвечивается и рядом
  появляется маленькая иконка ✎ — при наведении на неё всплывает
  подсказка «Изменено вручную» (сама подсказка не занимает места в
  строке). Если в `dashboard -> firebase` заполнены ключи — правки видны
  всем (пишутся в Firestore, коллекция `signal_overrides`); если нет —
  только в этом браузере (localStorage);
- **комментарии** — под каждым сигналом можно оставить произвольный
  текстовый комментарий (без имени автора). Работает только при
  настроенном Firebase (коллекция `signal_comments`) — без него блок
  показывает пояснение вместо формы, локального режима для комментариев
  нет;
- **два уровня сигналов** — переключатель «Уровень 1 / Уровень 2» над
  статистикой. Уровень 1 — сырой список от агента (те же 🟢/🟡/🔴), на
  каждой карточке уровня 1 — три кнопки голосования за исход 2-го
  уровня: 🗑 Отмели / 🤔 Сомнительно, но окей / 🔥 Очень интересно, у
  каждого варианта свой счётчик голосов. Как только любой из вариантов
  набирает `votes_to_promote` голосов (по умолчанию 3, настраивается в
  `config/parameters.yaml` или в админ-панели), сигнал переходит на
  Уровень 2 с этим статусом (🗑→серый, 🤔→жёлтый, 🔥→зелёный) и пропадает
  с Уровня 1. Счётчики голосов и кнопки остаются видимыми и после
  перехода на 2-й уровень — статус пересчитывается заново при каждом
  изменении голосов, а не фиксируется навсегда: если распределение
  голосов меняется, сигнал может вернуться на Уровень 1 (если ни один
  вариант больше не набирает порог) либо переехать в другую группу
  2-го уровня (например, из «Очень интересно» в «Отмели», если голосов
  за «Отмели» стало больше). Голосование открыто всем без логина, один
  голос с одного браузера на сигнал, но этот голос можно менять сколько
  угодно раз — клик по другому варианту снимает старый голос и
  засчитывает новый (счётчик у прежнего варианта уменьшается на 1). При
  настроенном Firebase голоса общие (коллекция `signal_votes`), без
  него — считаются только локально в этом браузере;
- **админ-панель** (значок ⚙️ у заголовка) — правит «на лету», без
  пересборки дашборда: пороги светофора, вес каждого критерия оценки,
  сколько голосов нужно для перехода на 2-й уровень, и информационное
  поле «частота обновления» (только отображается на дашборде, реальное
  расписание пайплайна не меняет — его правят в `.github/workflows/`).
  Правки пишутся в Firestore (`admin_config/config`) и применяются сразу
  у всех, кто открыл дашборд; без настроенного Firebase кнопка
  «Сохранить» неактивна — панель можно открыть и посмотреть текущие
  значения, но менять их можно только через `config/parameters.yaml`.

### Группы источников вместо tier

Вместо номеров tier источники делятся на именованные группы —
задаются в `config/parameters.yaml`:

```yaml
source_groups:
  "РФ/ТГ":
    description: "Русскоязычные СМИ и Telegram-каналы про HR-tech, рекрутинг, стартапы и рынок труда в России."
  "Мировой":
    description: "Англоязычные международные источники про HR-tech, стартапы, венчур и рынок труда."
```

а у каждого источника в `sources` — поле `group`, равное одному из
ключей выше (`group: "РФ/ТГ"` или `group: "Мировой"`). Названия и
описания групп — ваши, можно переименовать/добавить ещё группы в любой
момент, дашборд подхватит их при следующей сборке.

**Источники без RSS (в основном Telegram-каналы)** помечаются
`type: telegram` вместо `type: rss` — пайплайн их пока не читает
автоматически (см. раздел «Источники без RSS» ниже), но они всё равно
видны в подсказке у фильтра «Группа источника», чтобы список источников
в одном месте был полным.

### Как считается разбивка оценки

`src/analyze_signals.py` теперь просит модель оценить сигнал по
каждому критерию из `priority_weights` отдельно (JSON-объект
`criteria_scores`, 1-5 по каждому), а итоговый `priority_score` —
взвешенное среднее по весам из конфига считает сам Python, не модель
(так результат воспроизводим и не зависит от того, умеет ли модель
складывать числа). Обе величины пишутся в `data/backlog.csv`.

**Если у вас уже накоплен `data/backlog.csv` из прошлых запусков** —
структура файла менялась: `source_tier` и `criteria_scores` дописаны в
конец списка колонок, а не вставлены в середину, специально чтобы не
пришлось трогать существующие строки. Достаточно один раз вручную
поправить **первую строку файла** (заголовок), добавив в конец
`,source_tier,criteria_scores`. Старые строки останутся как есть — на
дашборде у них просто не будет тега группы и блока «Разбивка оценки»
(это ожидаемо, для них таких данных не было собрано), а новые строки
после следующего запуска будут заполняться полностью. Колонка
называется `source_tier` по историческим причинам (раньше в ней хранился
номер tier) — сейчас в ней хранится название группы источника, но
переименовывать колонку не стали, чтобы не заставлять вас ещё раз
вручную редактировать уже накопленный файл.

Без прикосновения к коду через `config/parameters.yaml -> dashboard`
можно поменять заголовок страницы (`title`) и акцентный цвет вкладок,
кнопок и активных фильтров (`accent_color`) — светофор при этом не
трогается, это отдельная, фиксированная по смыслу палитра (зелёный =
хорошо, жёлтый = требует внимания, красный = низкий приоритет). Сейчас
`accent_color` ориентирован на фирменный фиолетовый Авито — точный HEX
не подтверждён официальным брендбуком на момент подготовки, замените
на точное значение, если оно у вас есть.

Более глубокие изменения (другой набор полей на карточке, другая
раскладка) — правьте `TEMPLATE` и `render_card()` в
`src/build_dashboard.py` напрямую, это обычный Python + f-строки, без
дополнительных библиотек.

## Настройка параметров

Всё, что можно менять без прикосновения к коду, находится в
`config/parameters.yaml`: пороги светофора, веса критериев
приоритизации, список источников, целевое окно дат, модель для анализа.
Отредактируйте файл (в веб-интерфейсе GitHub или в VS Code), закоммитьте
— при следующем запуске пайплайн уже использует новые значения. История
изменений параметров — это обычная история коммитов этого файла
(`git log -- config/parameters.yaml`), отдельный журнал вести не нужно.

## Стоимость API и как её снижать

Деньги с ключа `ANTHROPIC_API_KEY` тратит только `analyze_signals.py` — по
одному вызову Claude на каждую новую статью, которая доходит до этого шага.
`fetch_sources.py` (чтение RSS) и `build_dashboard.py` (сборка HTML) —
бесплатные, к LLM не обращаются. Значит, стоимость прямо пропорциональна
числу статей, которые долетают до анализа — и это управляемо:

- **`require_market_match: true`** (`config/parameters.yaml`) — статья
  должна совпасть хотя бы с одним ключевым словом рынка (`markets ->
  <рынок> -> keywords`) ДО отправки в LLM, иначе отбрасывается бесплатно.
  Общие ленты вроде TechCrunch/CNews несут много статей мимо темы — это
  обычно самый большой рычаг экономии. Риск — пропустить сигнал,
  сформулированный непривычными словами мимо списка keywords; если это
  важнее экономии, поставьте `false`;
- **`llm -> model`** — `claude-sonnet-5` дешевле и новее, чем
  `claude-sonnet-4-5`, который стоял здесь раньше;
- дедуп по `source_url` в `data/backlog.csv` не даёт повторно
  анализировать уже виденные статьи при обычном еженедельном запуске —
  расход растёт в первую очередь на первом прогоне (там нет истории для
  сверки) и при `--mode backfill` по широкому диапазону дат.

## Осознанные упрощения этой версии (на что обратить внимание дальше)

- `cluster_id` не заполняется автоматически — кластеризация
  повторяющихся сигналов из разных источников оставлена на следующую
  итерацию (сейчас дедуп — только по точному совпадению ссылки).
- Источники ограничены RSS (см. пункт выше).
- Дашборд статический: обновляется при каждом запуске workflow, а не в
  реальном времени при каждом открытии страницы.
- Имя модели в `config/parameters.yaml -> llm.model` стоит проверить в
  консоли Anthropic перед первым запуском — актуальные названия моделей
  могут отличаться от того, что указано по умолчанию.

## Локальный запуск (необязательно)

```
pip install -r requirements.txt
cp .env.example .env   # и впишите туда свой ключ
export $(cat .env | xargs)
python src/run_pipeline.py --mode weekly
python src/build_dashboard.py
```
